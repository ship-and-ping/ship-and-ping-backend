# 쉽앤핑 T53 — 해결 판정에 요청량 비교 (부하가 줄어 정상처럼 보이는 경우 구분)

너는 Orca 작업 에이전트(Codex)다. 새 작업 폴더에서 일하고 PR까지 만든다. **머지 금지.** Windows — Rust·DB는 CI(`gh pr checks`), 웹은 로컬.
명령은 경로를 그대로 하나씩(셸 변수·명령 치환·인터프리터 한 줄 실행 금지), 파일은 Read·Write(편집) 도구로.

## 왜 (Trova 공동 시험에서 발견, 2026-11-28)
부하 시험 중 열린 느림 사건이 시험이 끝나 요청이 거의 없어진 뒤(재시작 버전에서 몇 건) '해결됨'으로 닫혔다. 실제로는 고쳐지지 않았는데 부하가 줄어 정상처럼 보인 것. 사용자는 해결 알림을 믿고 끝낸다 — 거짓 해결은 신뢰를 깬다.

## 먼저 읽기
`supabase/migrations/` 최신 `evaluate_all`·`private.verification_progress`(20261128005903_stall_recovery.sql, 005905_scoped_evaluation.sql), `web/src/issue-prompt.ts`·문제 상세 화면, `docs/` 판정 규칙 문서.

## 바꿀 것
1. 사건 개설 시 요청량(개설 10분 창의 분당 요청 수)을 metric_at_open에 저장(이미 있으면 재사용).
2. 해결 후보(새 버전 정상 5회)일 때, 최근 10분 분당 요청 수가 개설 때의 **20% 미만**이면 '해결됨' 대신 **'조용해짐 — 같은 부하에서 확인 필요'** 상태로 둔다(새 상태 또는 resolved+플래그 중 단순한 쪽, 근거 문서화). 알림 문구도 구분: "요청이 줄어 정상처럼 보여요. 같은 부하에서 다시 확인해 주세요".
3. 이후 요청량이 개설 때의 50% 이상으로 돌아온 상태에서 정상 5회면 진짜 해결로 전환.
4. 문제 상세·AI 요청문·MCP check_resolution에 요청량 비교(개설 때 분당 N건 → 지금 M건) 표시.
5. 저빈도 기능(개설 때 분당 요청이 원래 적은 경우, 예: 분당 2건 미만)은 비교 생략(지금처럼).

## 테스트 먼저
DB: 부하 감소 거짓 해결 재현(개설 200/분 → 해결 후보 때 3/분 → 조용해짐), 부하 회복 후 진짜 해결, 저빈도 생략. 웹: 문구. 변형 검사 한 번. 마이그레이션은 새 파일만.
