## 할 일
1. **문제 종류 판단(규칙 기반, 근거 함께)** — 지금 있는 기록으로: ① 서버 자원 부족(여러 기능 동시 + 요청량 급증 + 5xx 적음) ② 업데이트 후 고장(새 버전 직후 소수 기능, 요청량 평소) ③ 코드 오류 급증(5xx + 같은 오류 이름 반복) ④ 외부 서비스(특정 단계만 느림·시간 초과, 배포 없음) ⑦ 설정·인증(배포·키 교체 직후 401/403 급증) ⑧ 비정상 트래픽(한 기능만 폭증 + 4xx 급증) ⑨ 기록 끊김(T54의 silent). T54 데이터(CPU·DB 시간)가 있으면 ①⑤(DB)⑥(메모리 추이) 근거 강화, 없으면 '확인 필요'로. 판단 불가면 '종류 불명'.
2. **문제 상세 화면**에 "**○○로 보여요** — 근거: …(최대 3개), 확신: 높음/보통/낮음".
3. **종류별 요청문**(issue-prompt.ts): 공통 머리(무슨 일·시각 두 개·요청량·동시 장애·오류 정리 — T52) + 종류별 '판단 순서·확인 명령·고치는 방향·확인 방법'. 공통 꼬리:
   - **AI가 스스로 확인할 명령**: "추측하기 전에 서버에서 직접 확인해: `top -b -n1`, `vmstat 1 5`, `free -m`, 클라우드 콘솔 CPU 그래프(무료 서버는 steal 확인)" — 앱 프로필(T54)의 '서버 지표 보는 법'이 있으면 그걸 우선.
   - **바뀐 코드 범위**: 버전이 git 해시면 "`git log --oneline <이전해시>..<새해시>`와 `git diff --stat`부터 봐"(이전 버전이 해시가 아니면 생략).
   - **고친 뒤 확인**: 종류 ①이면 같은 부하로 재는 k6 최소 예시(사건의 기능·분당 요청 수로 채움), 그 외는 "배포 후 쉽앤핑이 새 버전에서 정상 5번 확인하면 해결". 쉽앤핑 MCP(T56)가 연결돼 있으면 "쉽앤핑 MCP의 get_incident/check_resolution으로 확인" 한 줄.
4. 키·개인정보 미포함 유지, 기존 보안 테스트 유지, 요청문 길이 상한.

## 테스트
종류별 판단 단위 테스트(트루바 사건 → ①, 새 버전 직후 단일 기능 → ②, 5xx 반복 → ③, 단계 시간 초과 → ④, 401 급증 → ⑦, 한 기능 폭증+4xx → ⑧, 근거 부족 → 불명), 요청문 스냅샷, 화면 문구. 변형 검사.
