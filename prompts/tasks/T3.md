## 할 일 (테스트 먼저)
1. 도구: Supabase CLI(무료). 로컬 테스트에 Docker가 필요하면 이 기기에 있는지 확인하고, 없으면 설치하지 말고 CI(GitHub Actions)에서 돌리는 방식으로 한다. 설치한 것·버전 보고.
2. `supabase/migrations/`: `db.md`의 테이블 13개, 인덱스, 제약(앱당 깊게 보기 5개·주소 형태 200개는 트리거), `app_keys.key_hash`는 회원에게 노출 안 되는 뷰, `alert_channels`의 슬랙 주소는 Vault(또는 pgsodium) 참조.
3. RLS: 회원은 `apps.owner_id = auth.uid()`인 앱과 하위 행만 SELECT. 회원이 쓸 수 있는 것은 앱 이름·주소, 기능 이름·숨김·느림 기준, 알림 설정뿐. 기록·문제 테이블 쓰기는 RPC만.
4. RPC (`security definer`, `search_path` 고정, 회원 실행 권한 없음 — `issue_key`만 회원용):
   - `ingest_batch(app_key_hash text, payload jsonb)`: 키 확인(폐기·만료), `batch_id` 중복 무시, 버전·기능 등록, `stats_5m` upsert(합산값 더하기), 오류 예시(기능·버전별 최근 20개 유지), 결과 `{accepted, dropped}`. payload 형식은 T2가 만드는 합산 결과와 맞춰야 하므로 **형식을 `supabase/README.md`에 JSON 예시로 확정해 적는다**(T2 지시문의 4.4 합산 항목과 같은 이름).
   - `suggest_feature_map`, `issue_key(app_id, kind)`(원문 한 번만 반환·해시 저장·재발급 시 이전 키 24시간), `record_notification`, `cleanup_daily`(30일 지난 5분 요약 → `stats_1h`, 오래된 행 삭제).
   - `evaluate_all`은 T6 몫 — 만들지 않는다.
5. 테스트(pgTAP 또는 SQL 테스트, `supabase/tests/`):
   - C1: 회원 A·B가 서로의 앱·기록·문제를 어떤 테이블·뷰로도 못 읽음, 회원이 기록 테이블에 직접 못 씀
   - 키: 폐기·만료 키로 `ingest_batch` 거부, 회원이 남의 앱 `issue_key` 불가, key_hash 비노출
   - `ingest_batch`: 중복 batch 무시, 합산 누적, 오류 예시 20개 유지
   - `cleanup_daily`: 30일 경계
   - 변형 검사: RLS 정책 하나를 빼면 C1 테스트가 실패하는지 확인 후 복구
6. CI `.github/workflows/db.yml`: `supabase/**` 변경 시 로컬 Supabase(또는 Postgres 서비스 + 필요한 auth 스텁)로 마이그레이션 적용과 테스트. 외부 액션은 커밋 SHA로 고정. 비밀값 불필요해야 한다.
7. `supabase/README.md`: 로컬 실행·테스트 방법, `ingest_batch` payload 형식, 운영 프로젝트에 적용하는 방법(사용자가 프로젝트를 만든 뒤 — 실제 적용은 하지 않는다).
8. 이 지시문을 `prompts/tasks/T3.md`로 저장.

## 지킬 것
- 셸 변수·명령 치환(`$(...)`)·`eval`을 쓰지 말고 경로를 그대로 써서 명령을 나눠 실행하라(가드에 막힌다). 파일은 편집 도구로 쓴다.
- 실제 Supabase 프로젝트(원격)에 연결·적용하지 않는다(계정 없음, 운영 DB 변경 금지). 비밀값 커밋 금지. 유료 서비스 금지.
- 요청 원본 저장 금지(5분 요약만), 개인정보 열 만들지 않기(기능명세서 4.2).
- Windows에서 쓰기가 막혀 있으면 바로 그 사실과 오류를 보고하고 멈춘다.
