# 쉽앤핑 D6 — 웹 전체 UI·UX 디자인 QA + 모션 다듬기 (밤샘 작업)

너는 Orca 작업 에이전트(Codex)다. 새 작업 폴더에서 일하고 PR까지 만든다. **머지 금지.** 사용자는 자는 중이라 질문할 수 없다 — 막히면 가정을 적고 안전한 쪽으로 진행, 결정이 꼭 필요한 것은 PR 본문 '사용자 결정 필요'에 모은다.
명령은 경로를 그대로 하나씩 쓴다. 셸 변수·명령 치환·인터프리터 한 줄 실행(`python -c`, `node -e`) 대신 경로를 그대로 쓰고 파일은 Read·Write(편집) 도구로 다룬다.

## 목표
이미 만든 웹(`web/`)의 모든 화면을 실제 브라우저로 열어 디자인·사용성 문제를 찾고, **기존 디자인 시스템 안에서** 고친다. 모션(움직임)도 다듬는다. 새 디자인 방향을 만드는 작업이 아니다(방향은 C안으로 확정됨).

## 레퍼런스 (사용자 선택: 추천대로)
가져올 것은 **흐름·문장·캐릭터 쓰는 법·모션**뿐이다. 색·로고·글꼴·일러스트를 베끼지 않는다.
- 토스(https://toss.im): 한 화면에 한 메시지, 짧은 문장과 줄바꿈, 스크롤하며 하나씩 보여 주는 소개 흐름, 큰 글씨 위주
- 듀오링고(https://www.duolingo.com): 캐릭터가 상태에 따라 표정·동작이 바뀌는 방식(기다림·문제·해결), 짧고 친근한 문구
- Raycast(https://www.raycast.com): 어두운 배경 위 제품 화면을 크게 보여 주고 대비를 주는 법
사이트를 직접 열어 볼 수 있으면 보고, 못 열면 위 설명만으로 판단하고 PR에 '열어 보지 못함'이라고 적는다.

## 색 — 반드시 쉽앤핑 색만 (사용자 지시)
`web/src/styles/tokens.css`의 토큰만 쓴다: 진보라 #261B40(--sp-btn/--sp-hero), 라벤더 #C3A6FF(--sp-hero-btn), 민트 #76E7C4(--sp-ok), 주황 #FF8A65(--sp-bad) 등. 새 색을 하드코딩하지 않는다. 꼭 필요한 새 값은 토큰으로 추가하고 이유·대비값을 주석으로. 밝은·어두운 모드 둘 다.

## 화면 띄우는 법 (로그인 없이)
실제 Supabase 로그인은 메일 링크가 필요해서 너는 못 한다. 대신:
- `web/.env.local`을 만든다(커밋 금지, .gitignore 확인): `VITE_SUPABASE_URL=https://example.supabase.co`, `VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_qa_local_only`, `VITE_INGEST_URL=https://ingest.ship-and-ping.invalid`
- Playwright(웹 폴더의 devDependency로만, 전역 설치 금지)로 개발 서버를 열고, `page.route`로 Supabase 요청(`/auth/v1/*`, `/rest/v1/*`)을 가로채 **가짜 데이터**를 돌려준다. 로그인 세션도 가짜로 넣는다. 앱 코드에 테스트용 우회 코드를 넣지 않는다.
- 상태별로 다 본다: 빈 화면(앱 0개·기록 대기), 정상, 문제 있음(실패·느림·결과 미확인), 해결됨, 로딩, 오류(요청 실패). 화면 폭은 PC 1440, 노트북 1280, 휴대폰 390. 밝은·어두운 모드, 글자 200% 확대, 동작 줄이기(prefers-reduced-motion).
- 이 QA 도구는 `web/qa/`에 두고 `npm run qa:shots` 같은 스크립트로 다시 돌릴 수 있게 한다. 캡처는 `docs/design/qa/before/`, `docs/design/qa/after/`에 같은 파일명으로(PNG, 너무 크면 JPG 품질 80).

## 검사 항목 (UX 검토 체크리스트)
- 사용자 목표: 비전공자가 "내 앱 지금 괜찮나 → 뭐가 문제 → AI에 붙여넣기 → 고쳐졌나"를 막힘 없이 하는가
- 정보 구조·우선순위, 버튼 문구(누르면 무슨 일이 일어나는지 알 수 있나), 뒤로 가기·취소
- 로딩(진행 표시·중복 제출 방지), 빈 화면(이유와 다음 행동), 오류(무엇이·어떻게 고치나, 입력 유지), 완료(성공했는지·다음 할 일)
- 한글 글꼴·줄바꿈(`word-break: keep-all`, 어색한 한 글자 줄 없음), 글자 크기 단계, 간격 리듬, 정렬
- 접근성: 대비(글자 4.5:1, 그래픽 3:1), 키보드만으로 전부 가능, 초점 표시, 화면 읽기 이름, axe 검사(vitest-axe 이미 있음)
- 휴대폰 폭에서 가로 스크롤 없음, 누르기 쉬운 크기(44px)

## 모션 (사용자 요청)
- 소개 페이지(S0): 스크롤에 따라 섹션이 차례로 나타나기(토스식), 양 캐릭터가 상자 밖에서 움직이기(살짝 떠 있기·두리번·핑 신호). 과하지 않게.
- 앱 화면: 상태 변화를 알려 주는 모션만 — 카드 상태 전환(대기→정상→문제→해결), 복사 완료 피드백, 버튼 누름 반응, 화면 전환, 스켈레톤 로딩. 양 캐릭터 표정·동작을 상태별로(기다림·걱정·안심) — 듀오링고식.
- 규칙: transform·opacity만 애니메이션, 150~300ms 중심, 반복 동작은 눈에 거슬리지 않게, `prefers-reduced-motion`이면 움직임 끄기, 키보드·자주 누르는 동작엔 모션 빼기. 라이브러리는 이미 있는 것 우선, 새로 넣으면 이유를 적고 가벼운 것만(무료·MIT 등).

## 도구
이 기기에서 실제로 쓸 수 있는지 먼저 확인하고, 쓴 것과 그 도구가 바꾼 결정을 PR에 적는다(안 쓴 것을 썼다고 하지 않는다).
- 중심: `impeccable`(기존 화면 평가·고칠 순서) — 없으면 같은 체크리스트로 직접
- 보완: `emil-design-eng`(모션 속도·감속·타이밍), `ui-ux-pro-max`(공통 규칙·UX 패턴)
- 새 도구 설치 금지(설치는 보안 검토가 먼저다). 비용 드는 글꼴·에셋·서비스 금지.

## 진행
1. before 캡처 전부 → 문제 목록(심각도: 막힘/헷갈림/다듬기)을 `docs/design/qa/2026-11-26-qa.md`에 표로.
2. 막힘 → 헷갈림 → 다듬기 순으로 고친다. 고칠 때마다 관련 테스트 먼저(문구·상태·접근성·reduced-motion). 기존 테스트 깨지지 않게.
3. 모션 적용.
4. after 캡처 → QA 문서에 "찾은 것 → 고친 것 → 전/후 캡처 경로" 표, 못 고친 것과 이유, 남은 가정.
5. `docs/design/qa/index.html` 한 장: 화면별 전/후를 나란히 보는 비교 페이지(사용자가 아침에 이것만 열어 보면 되게).
6. 이 지시문을 `prompts/tasks/D6.md`로 복사, 위임 로그 6칸(목표·프롬프트·결과·검증·수정·배운점 한줄)은 PR 본문.

## 지킬 것
- 범위: `web/`, `docs/design/qa/`, `docs/design-system.md`(모션 규칙 추가 시), `prompts/tasks/D6.md`. `worker/`·`supabase/` 건드리지 않는다.

- 키 모양 리터럴 금지(위 가짜 값처럼 명백한 가짜만), 실제 외부 서비스 연결 금지, `.env.local` 커밋 금지.
