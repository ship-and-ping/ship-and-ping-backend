# 쉽앤핑 T6 — 판정(Cron)과 evaluate_all: 평소 속도·경보·해결

너는 Orca 작업 에이전트(Codex)다. 새 작업 폴더에서 일하고 PR까지 만든다. **머지하지 않는다.**
기준 브랜치는 **아직 병합 전인 T4 브랜치(`origin/feat/T4-ingest-worker`)**다 — Worker 구조가 거기서 바뀌었다. 나중에 T4가 main에 합쳐지면 `origin/main`을 merge한다.
같은 시간에 다른 작업자가 `web/`(T7)를 만든다 — `web/`은 건드리지 않는다.

## 먼저 읽기
- 기능명세서 5.4(경보·복구 기본 기준), 7장(판정 규칙 표 전체), 8장(알림 — 이번엔 '보낼 목록'까지만), 9장 예외, 10장 C6·C7·C8·C10
- `db.md`(stats_5m·stats_1h·attempts·baselines·incidents·notifications·app_versions), `supabase/migrations/`, `supabase/tests/`
- `worker/` 구조(T4 브랜치), `docs/research/2026-11-24-free-tier-constraints.md` 1장(CPU 10ms·Cron 5개)

## 맡은 파일
`supabase/migrations/`(새 파일만), `supabase/tests/`(새 파일), `worker/src/`의 Cron 진입점·판정 호출 모듈(새 파일 위주, 기존 수집 코드는 최소 변경), `worker/wrangler.toml`의 cron 설정, `prompts/tasks/T6.md`.

## 만들 것 (테스트 먼저)
1. **DB 함수 `evaluate_all()`** (security definer, search_path 고정, Worker의 secret 키 역할만 실행): 무거운 계산은 전부 여기서.
   - 깊게 보기 시도: 시작 후 10분 결과 없음 → `unconfirmed`.
   - 평소 속도(baselines): 성공 30건 이상 & 첫 기록 후 3일 → 최근 7일 성공의 중앙값·90% 지점(hist 16구간으로 근사), 6시간마다 갱신. 그 전엔 관측 최소·최대·건수만.
   - 실패 경보: 최근 30분 결과 5건 이상 & 실패 20% 이상, 또는 깊게 보기 연속 실패 3건.
   - 느려짐 경보: 최근 30분 5건 이상 & 중앙값 ≥ 평소 중앙값×2. 평소 속도 없으면 느림 기준(기본 5000ms) 넘는 요청이 절반 이상.
   - 결과 미확인 급증: 최근 1시간 미확인 50% 이상 & 10건 이상.
   - 묶기: 같은 앱·기능·종류의 열린 문제가 있으면 새로 열지 않음. 다시 알림: 처음보다 2배 이상 나빠지고 마지막 알림 후 6시간.
   - 해결: 문제 시작 후 새 버전(app_versions에서 문제 열린 뒤 처음 본 버전)에서 결과 5건 연속 성공(느려짐은 평소의 1.5배 이내) → resolved. 버전 변화 없이 2시간 기준 미만 → quiet(알림 없음). '문제 아님'(dismissed_until 24시간) 존중.
   - 결과: 이번 회차에 생긴 일(열림·더 나빠짐·해결) 목록을 JSON으로 반환(알림 보낼 목록). 실제 발송은 T8.
2. **`cleanup_daily()`** 이미 있으면 Cron 연결만.
3. **Worker Cron**: 1분마다 `evaluate_all` RPC 1회 호출(CPU 최소), 하루 1회 `cleanup_daily`. 결과 목록은 지금은 로그·`notifications`에 '대기'로 기록(T8이 발송). Cron 트리거는 2개 이내(무료 5개 한도).
4. **pgTAP 테스트**(시나리오 데이터로): C6(실패 20%·느려짐 2배·미확인 급증 각각 열림, 같은 문제 알림 1번), C7(새 버전 5건 연속 성공 → resolved, 사용 없음 → 대기), C8(30건·3일 전엔 평소 속도 없음), quiet·dismissed·다시 알림 6시간·2배, 경계값(4건 vs 5건, 19% vs 20%).
5. 성능: `evaluate_all`이 앱 20개·기능 15개·30분 데이터에서 몇 ms인지 pgTAP 또는 explain으로 측정해 PR에.
6. 이 지시문을 `prompts/tasks/T6.md`로, 위임 로그 6칸은 PR 본문.

## 지킬 것
명령은 경로를 그대로 하나씩(셸 변수·명령 치환·인터프리터 한 줄 실행 금지), 파일은 편집 도구로. 키 모양 리터럴 금지. 실제 Supabase·Cloudflare 연결 금지.

## PR

# 쉽앤핑 T6 검증 지적 수정 (PR #12, 브랜치 feat/T6-evaluate)

너는 Orca 작업 에이전트(Codex)다. 기존 작업 폴더(feat/T6-evaluate)에서 이어서 고치고 같은 PR #12에 일반 push. 머지·강제 push 금지.

## 시작
`git fetch origin` → `git merge origin/feat/T4-ingest-worker`(T4가 4342a28까지 갱신됨, PR #10 내용 포함). 충돌 해결.

## 고칠 것 (테스트 먼저)
1. **(높음) 마이그레이션 번호**: `20261125000600_evaluation_inputs`·`0610` 등 T6 마이그레이션을 base의 가장 큰 번호(현재 `20261125001200_lookup_key_app` 이후) 다음으로 다시 번호 매기기. base 전체 마이그레이션 위에서 pgTAP 전부 통과 확인.
2. **(중간) 알림 발송 준비(T8용)**:
   - 대기 알림을 **채널별 행**으로(슬랙과 이메일 둘 다 켠 회원은 두 행). 채널 설정이 없으면 화면 표시만.
   - `claim_notifications(limit)`: 대기 행을 선점(FOR UPDATE SKIP LOCKED, 선점 시각 기록, 오래된 선점은 재시도 가능)해 반환, `complete_notification(id, ok, error)`: 완료 처리(error는 가림 후 저장). 둘 다 service_role 전용, security definer, search_path 빈 값.
   - `cleanup_daily`가 30일 지난 알림 행(대기·완료 모두)을 정리.
   - `db.md`에 이 테이블·함수 반영(이 PR에서 허용).
3. **(중간) 되돌린 옛 버전**: 문제 시작 후 다시 나타난 버전(예전에 본 버전)도 '문제 이후 버전'으로 인정 — app_versions에 last_seen_at 또는 재등장 기록을 써서 판단(명세 9장 '다시 나타난 버전').
4. **(중간) 느려짐 정도 단위 통일**: 평소 속도 생성 전후 모두 같은 단위(배수 또는 비율 하나)로 저장·비교해 거짓 '더 나빠짐' 알림이 없게.
5. **(낮음)** 현재 중앙값은 성공 결과만으로(평소와 같은 기준); 깊게 보기 평소값은 구간 상한 대신 구간 내 보간; 해결 판정의 순서는 **서버 수신 시각** 기준(클라이언트 시각 무시); 실패율 50% 넘게 열린 문제는 '2배' 다시 알림 대신 '실패 건수 2배'로 정의하고 명세 7장 문구에 반영(이 PR에서 명세 7장만 수정 허용).
6. **(낮음) 요청 단위 저장**: 해결 판정용 최근 결과(latest_results)는 기능·버전별 최근 20건만 남기고 30일 정리 — 명세 4.4·db.md에 '해결 판정용 최근 20건 예외' 한 줄 추가.
7. **테스트 공백**: 평소 속도 없을 때 느려짐 열림, 못 미치는 경계(slow 4건·1.9배, missing 9건·49%, 10분 미만), quiet 2시간 미만·새 버전 차단, 문제 전 버전으로 해결 안 됨, 되돌린 버전으로 해결, dismissed 만료, advisory lock(동시 호출), 4xx 분모 제외, 알림 선점·완료·정리, 채널별 행.
8. **성능**: 앱 20 × 기능 15에 **7일치** 5분 요약(평소 속도 계산 포함)을 넣고 evaluate_all 시간을 재서 PR에 표로.
