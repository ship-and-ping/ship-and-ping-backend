# Ship & Ping(쉽앤핑) 기능명세서 v1.1

표시: **[PRD]** PRD에서 확정 · **[제안]** 이 문서의 제안 · **[결정 필요]** 0장 질문의 답에 따라 바뀜

## 0. 결정 사항 — 2026-11-25 사용자 "추천대로": D1=A, D2=A, D3=A, D4=A

### D1. 모니터링 엔진 — **추천: 판정은 쉽앤핑이 직접, Grafana는 운영자 내부용만**
조사 결과 Grafana Cloud 이용약관이 서비스 **재판매(resell)를 금지**하고, 사용 범위를 "개인 사용·자기 회사 내부 운영"으로 한정한다(https://grafana.com/legal/terms/ 10조·13.2조). 무료 계정 하나에 여러 회원의 앱 기록을 받아 서비스로 제공하면 약관 위반 소지가 있다. 무료 한도(지표 1만 개·사용자 3명·규칙 500개)도 모든 회원이 나눠 써야 한다.

| 선택지 | 내용 |
|---|---|
| **A (추천)** | 기록 받기·평소 속도·경보·해결 판정을 쉽앤핑(Rust Worker + Supabase)이 직접 한다. Grafana Cloud는 **운영자가 쉽앤핑 자체를 지켜보는 용도**(내부 운영 → 약관 허용 범위)로만 쓴다. 회원 화면·알림은 PRD와 똑같다 |
| B | PRD대로 Grafana를 회원용 엔진으로 쓰되, 시작 전에 Grafana에 서면으로 허용을 받는다. 답이 올 때까지 개발 시작이 늦어진다 |
| C | Grafana 오픈소스를 직접 서버에 설치(AGPL, 재판매 제한 없음). 서버 비용·관리가 생겨 무료 목표와 충돌 |

이 문서는 **A 기준**으로 썼다. A를 고르면 PRD 1장·7장의 "모니터링 엔진" 줄만 고친다.

### D2. 앱이 보내는 기록 형식 — **추천: 쉽앤핑 전용의 간단한 JSON 묶음**
Workers 무료 플랜은 요청당 CPU 10ms다. OpenTelemetry 표준(protobuf)은 Rust wasm에서 빌드·속도가 확인되지 않았다.
| 선택지 | 내용 |
|---|---|
| **A (추천)** | 쉽앤핑 형식(JSON, 최대 100건 묶음). 코딩 AI가 작은 전송 코드를 직접 쓴다. 가볍고 검사하기 쉽다 |
| B | OpenTelemetry 표준. 자동 연결 도구가 많지만 첫 작업 PoC가 실패하면 늦어진다 |

### D3. 이메일 — **추천: Resend 무료(하루 100건) 사용, 계정은 사용자가 만든다**
Cloudflare 무료 메일은 인증한 주소로만 보낼 수 있어 회원 알림에 못 쓴다. Supabase 기본 메일도 시간당 2건이라 운영 불가.
| 선택지 | 내용 |
|---|---|
| **A (추천)** | Resend 무료 계정(비용 0원). 알림 메일과 가입 메일 모두 여기로 |
| B | 첫 버전은 이메일 없이 슬랙 + 화면만, 로그인은 Google만 |

### D4. 로그인 방식 — **추천: Google 로그인 + 이메일 링크 로그인**
| 선택지 | 내용 |
|---|---|
| **A (추천)** | Google 로그인(메일 발송 불필요) + 이메일 링크(D3이 A일 때) |
| B | Google 로그인만 |
| C | 이메일·비밀번호 |

## 1. 전체 구조 [제안, D1=A 기준]

```
제작자 웹앱 (브라우저 / 서버)
   │  POST /v1/ingest  (수집 키, JSON 묶음)
   ▼
수집 Worker (Rust, Cloudflare Workers)
   │  키 확인 → 검사·정제 → 묶음 안에서 5분 단위로 합산
   │  Supabase RPC 1번 호출 (sb_secret 키)
   ▼
Supabase PostgreSQL ◀──── 웹 화면(React)이 로그인 세션으로 직접 읽음 (행 수준 권한)
   ▲
   │ 1분마다 RPC evaluate_all()
판정 Worker (Cron) ──▶ 문제 열기·닫기 결과 받음 ──▶ 슬랙 / 이메일(Resend)
   
운영자: Grafana Cloud가 Supabase를 읽기 전용 계정으로 조회 (쉽앤핑 자체 상태만)
```
- 무거운 계산(평소 속도, 경보 판정)은 DB 함수가 한다 → Worker CPU 10ms 안에 맞춘다.
- 웹 화면 조회는 Worker를 거치지 않고 Supabase에 직접(브라우저에는 `sb_publishable_` 키만). Worker 요청 수 절약.
- Worker가 하는 일: 기록 받기, 기능 이름표 받기, 키 발급·재발급, 슬랙 연결 콜백, 판정·알림(Cron).
- Cron 1분 실행은 Supabase가 1주 활동 없음으로 일시정지되는 것도 막는다.

## 2. 사용자와 권한

| 주체 | 무엇으로 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|---|
| 회원 | Supabase 로그인 세션 | 자기 앱 등록·조회·수정·삭제, 알림 설정, 로그아웃, **자기 계정 회원 탈퇴(본인만)** | 남의 앱 조회(행 수준 권한으로 차단), 다른 회원 탈퇴 |
| 수집 키 `sp_pub_…` | 제작자 앱(브라우저에도 노출됨) | 자기 앱으로 기록 보내기, 기능 이름표 **제안** 보내기, 깊게 보기 결과 중 `source=browser` | 조회 전부, 다른 앱으로 보내기, `source=server` 결과 |
| 서버 키 `sp_srv_…` | 제작자 서버(비공개) | 수집 키 권한 + `source=server` 결과 | 조회 |
| 수집·판정 Worker | `sb_secret_` 키(Cloudflare 비밀 설정) | 정해진 RPC 함수만 호출 | — |
| 운영자 | Grafana 읽기 전용 DB 계정 | 전체 수치 조회 | 쓰기 |

- 키는 DB에 **해시로만** 저장하고, 발급 직후 한 번만 화면에 보여 준다. 앞 8글자(접두)는 목록 표시용으로 남긴다.
- 재발급하면 이전 키는 **24시간 뒤** 무효(배포할 시간을 준다). [폐기]는 즉시 무효.
- 회원 탈퇴는 **본인만** 한다. 요청은 로그인 세션으로 하고, 서버가 세션의 사용자와 탈퇴 대상이 같은지 확인한다. 로그인 이메일을 다시 적어야 진행한다(S11).

## 3. 화면별 동작

공통: 브랜드 색(퍼플 `#261B40` 바탕, 라벤더 `#C3A6FF` 강조, 민트 `#76E7C4` 정상 상태), 쉬운 한국어, 주소·오류 원문은 [자세히] 안에만. 상태 표시는 세 가지: **괜찮아요**(민트) · **문제 있어요**(경고색) · **기록을 기다려요**(회색).

### S1. 첫 화면·로그인
- 서비스 소개 한 줄 + 마스코트 + [시작하기]. 로그인 방식은 D4.
- 첫 로그인이면 S3(앱 등록)으로 바로 보낸다.

### S2. 내 앱 목록
- 앱 카드: 이름, 상태, 열린 문제 수, 마지막 기록 시각("3분 전").
- 앱이 없으면 빈 상태 + [앱 등록하기].
- 무료 베타 한도: 회원당 앱 3개 [제안]. 넘으면 버튼 비활성 + 안내.
- 머리말 오른쪽 계정 아이콘 → S11 내 계정 (v1.1).

### S3. 앱 등록
- 입력: 앱 이름(필수, 1~40자), 앱 주소(선택, https URL 형식 검사).
- [등록] → 수집 키·서버 키 발급 → S4.

### S4. 연결하기
1. **[연결 요청 복사]** — 코딩 AI용 요청문(6장 틀). 키 값이 들어 있으므로 "이 요청문은 다른 사람에게 보내지 마세요" 안내.
2. 대기 화면: "첫 기록을 기다리고 있어요" + 진행 단계(① 요청문 복사 ✓ ② 코딩 AI가 연결 ③ 배포 ④ 앱 한 번 써 보기).
3. 기록이 오면 실시간 갱신(5초 간격 조회) → "기록이 도착했어요. 기능 N개를 찾았어요."
4. 기능 이름표 확인: 코딩 AI가 보낸 제안 목록(주소 → 이름). 이름 고치기, [이 기능 숨기기], [모두 확인]. 이름표가 없거나 누락된 주소는 주소 그대로 "이름 없는 기능"으로.
5. 30분 지나도 기록이 없으면 "기록이 안 와요?" 체크리스트 펼침: 배포했나요 / 앱을 한 번 써 봤나요 / 코딩 AI에게 이 문장 붙여넣기("쉽앤핑 연결이 동작하는지 확인해 줘: …" — 연결 확인 방법 포함).

### S5. 앱 홈
- 맨 위: 열린 문제 카드(있으면). 문장 예: "분석이 느려졌어요. 평소 1.1초 → 최근 30분 3.4초 (24건)".
- 기능 목록(최근 24시간 사용 많은 순): 이름, 상태, 사용 건수, 실패 건수, 보통 걸린 시간 / 평소 속도.
  - 평소 속도가 아직 없으면 "지금까지 7건, 0.9~2.1초" [PRD].
- 최근 업데이트 띠: "새 버전 v2025-11-24-1 감지 (14:02)" → S7의 해결 확인으로 연결.
- [깊게 볼 기능 추가] (S8), [설정] (S9·S10).

### S6. 기능 상세
- 요약 문장 + 최근 24시간·7일 막대(사용 건수, 실패 건수)와 보통 시간 선.
- 버전별 비교 표(최근 3개 버전): 건수, 실패율, 보통 시간.
- [자세히]: 주소 형태, 오류 종류별 건수, 최근 오류 예시 5개(정제된 문장).
- 기능별 "느림 기준"(기본 5초) 바꾸기 — 평소 속도가 없을 때만 쓰인다.

### S7. 문제 상세
- 제목 문장, 시작 시각, 현재 상태(진행 중 / 해결됐어요 / 잠잠해졌어요 / 문제 아님으로 닫음).
- 흐름: 처음 감지 → 알림 보냄 → 더 나빠짐 → 새 버전 감지 → 해결 판정.
- **[AI에 보낼 내용 복사]** (6장 틀).
- 업데이트 후 확인 영역:
  - 새 버전이 아직 없으면: "고친 버전을 배포하면 여기서 확인해 드려요"
  - 새 버전 있고 사용 없음: "업데이트 후 첫 사용을 기다리고 있어요" [PRD]
  - 진행 중: "업데이트 후 3건 성공, 2건 더 확인할게요"
  - 해결: "업데이트 후 분석 15건 모두 평소 속도로 끝났어요" [PRD]
  - 새 버전에서도 실패: "업데이트 후에도 5건 중 2건 실패했어요" + [AI에 다시 보낼 내용 복사](이전 시도 버전 포함)
- [문제 아님으로 닫기] — 같은 기능·종류는 24시간 동안 다시 열지 않음.

### S8. 깊게 볼 기능 추가 (앱당 최대 5개 [PRD])
- 입력: 기능 이름(예: 모임 신청), 시작(예: "신청 버튼을 누를 때"), 실제 성공(예: "참가자 명단에 저장됐을 때").
- [추가 연결 요청 복사] → 대기 → 첫 결과가 오면 "첫 신청 기록이 도착했어요. 참가자 명단에 저장되기까지 1.2초 걸렸어요" [PRD].
- 이 기능 카드에는 성공·실패·중단·결과 미확인을 따로 표시 [PRD].

### S9. 알림 설정
- **[Slack에 추가]** → Slack OAuth(`incoming-webhook`) → 채널 선택 → 콜백에서 webhook 주소 암호화 저장 → "#채널에 연결됐어요" + [시험 알림 보내기].
  - 실패 안내: 무료 워크스페이스 앱 10개 한도, 관리자 제한(`action_prohibited`)을 쉬운 말로.
- 이메일 알림 켜기/끄기(D3). 받는 주소는 로그인 이메일.
- 둘 다 꺼져 있으면 화면 상단에 "알림을 받을 곳이 없어요" 띠.

### S10. 앱 설정
- 이름·주소 수정, 기능 이름표 편집, 숨긴 기능 되살리기.
- 키: 접두만 표시, [재발급](이전 키 24시간 유지), [폐기](즉시).
- [앱 삭제]: 앱 이름을 다시 입력해야 삭제. 모든 기록 즉시 삭제.

### S11. 내 계정 (v1.1 추가, 사용자 결정 2026-11-25 "마이페이지도 추가해줘")
- 들어가는 길: S2 내 앱 목록 머리말 오른쪽 계정 아이콘(휴대폰·PC 같은 자리). 글자 200%에서는 [메뉴] 안 "내 계정".
- 계정 정보: 로그인한 이메일, 로그인 방식(Google / 이메일 링크).
- 알림 받을 곳 요약: 앱마다 슬랙 연결 상태·이메일 켜짐/꺼짐 한 줄. 누르면 그 앱의 S9. 받을 곳이 없는 앱은 "받을 곳 없음, 설정해 주세요".
- 내 앱 요약: 등록한 앱 수("3개 / 3개", 무료 베타 3개까지) + [내 앱 목록 보기].
- [로그아웃]: 이 기기의 세션만 끝낸다. 알림은 계속 간다. → S1.
- [회원 탈퇴] → 확인 화면:
  - 지워지는 것을 쉬운 말로 먼저 보여 준다: 모든 앱과 그 안의 기록·문제·알림 설정, 앱에 넣은 키 폐기(DB에서는 즉시 지우고, 수집 Worker의 키 캐시가 5분이라 **늦어도 5분 안에** 그 키로 온 기록은 401), 슬랙·이메일 알림 중단, 되돌릴 수 없음.
  - 로그인 이메일을 다시 적어야 [모든 앱과 기록을 지우고 탈퇴] 단추가 눌린다.
  - 진행 중: 단추 "탈퇴하는 중"(다시 눌리지 않음), 입력 잠금. 서버 순서는 키 폐기 → 앱 연쇄 삭제(기록·문제·알림 설정·이름표) → 로그인 계정 삭제.
  - 실패: "탈퇴를 마치지 못했어요" + 계정 상태(아직 남아 있고 로그인 됨) + [다시 시도](남은 삭제를 이어서). 적은 이메일은 지우지 않는다.
  - 완료: 로그아웃된 S1으로, 맨 위에 "탈퇴를 마쳤어요" 띠 한 번.
  - 확인 칸은 비어 있게 시작하고, 적은 값이 로그인 이메일과 정확히 같을 때만 단추가 눌린다. 실패 화면의 할 일은 [다시 시도] 하나(따로 탈퇴 단추를 두지 않음).
- **키가 멈추는 시점**: 수집 Worker는 키 해시를 메모리에 5분 캐시한다(5.1). Workers 메모리는 인스턴스마다 따로라 탈퇴 때 모든 캐시를 즉시 비울 방법이 없다. 그래서 탈퇴(와 S10 [폐기])는 DB의 키를 즉시 지우고, **늦어도 5분 안에** 모든 인스턴스가 401을 돌려준다고 약속한다. 그 5분 사이에 들어온 기록은 앱이 이미 지워져 저장되지 않는다(RPC `ingest_batch`는 앱을 찾지 못한 묶음을 저장하지 않고 버려야 한다 — 구현 때 확인). 화면 문구도 "늦어도 5분 안에 멈춰요"로 쓴다.
- **응답이 끊겼을 때 완료/실패 판별**: 탈퇴 요청을 보낸 뒤 응답 없이 연결이 끊기거나 시간이 넘으면(30초), 화면은 "탈퇴 결과를 확인하는 중"을 보이고 세션 갱신(다시 로그인 시도)을 한 번 한다.
  - Supabase Auth가 "사용자 없음"(세션 갱신 실패: 계정 삭제됨)이면 **완료**로 보고 S1 + "탈퇴를 마쳤어요".
  - 계정이 아직 있으면 **실패**로 보고 실패 화면 + [다시 시도]. 탈퇴 엔드포인트는 같은 요청을 여러 번 받아도 남은 단계만 하므로(멱등) 다시 시도해도 안전하다.
  - 세션 갱신도 네트워크 오류면 결과를 단정하지 않고 "결과를 확인하지 못했어요. 인터넷 연결을 확인하고 다시 열어 주세요"와 [다시 확인]을 보인다.
- 구현 메모: 로그인 계정 삭제는 Supabase Auth 관리자 권한이 필요하다 → 브라우저가 아니라 Worker 엔드포인트에서 세션 확인 후 처리하고, apps를 연쇄 삭제한다(db.md는 구현 작업에서 보강).

## 4. 수집 데이터

### 4.1 받는 것
| 종류 | 필드 | 규칙 |
|---|---|---|
| 묶음 공통 | `spec` (`"sp-1"`), `batch_id`(UUID), `app_version`(1~64자), `platform`(`browser`/`server`), `sent_at` | 필수 |
| 요청 기록 `request` | `route`(주소 형태, 최대 200자), `method`, `status`(정수), `duration_ms`(0~600000), `ts`, `error_kind`(선택, 최대 80자), `error_message`(선택, 최대 300자) | 같은 묶음 안에서 합산 |
| 깊게 보기 시작 `attempt_start` | `feature_key`, `attempt_id`(UUID), `ts` | |
| 깊게 보기 결과 `attempt_result` | `feature_key`, `attempt_id`, `result`(`success`/`failure`/`abandon`), `source`(`server`/`browser`), `ts`, `step`(선택, 실패한 단계 이름), `error_kind`·`error_message`(선택) | `source=server`는 서버 키만 |

### 4.2 받지 않는 것 [PRD]
입력값(이름·전화·이메일), 요청·응답 본문, 쿠키·토큰, 쿼리 문자열, 주소 안의 실제 값, 사용자 계정 ID.

### 4.3 수신 때 정제 (Worker)
- `route`: 쿼리 문자열 제거, 숫자·UUID·16자 이상 영숫자 조각 → `:id`. 앱당 주소 형태 200개 초과분은 "기타"로.
- `error_message`: 이메일·전화번호·`Bearer …`·`sk_`·`eyJ…`(JWT) 모양 → `[가림]`, 300자 자르기.
- `ts`: 받은 시각 기준 ±24시간 밖이면 버림.

### 4.4 저장 형태
- 요청 기록은 **원본을 저장하지 않고** 5분 단위 요약(앱·기능·버전·5분)으로만 저장: 건수, 실패(5xx·예외), 사용자 오류(4xx), 시간 합계, 시간 구간별 건수(중앙값·느린 쪽 계산용).
- 오류 예시는 기능·버전별 최근 20개만(정제된 것).
- 깊게 보기 시도는 시도 단위로 저장.
- 보관 [PRD]: 5분 요약·시도·오류 예시·문제·알림 30일, 시간별 요약 1년. 매일 Cron이 정리.

## 5. 기록 수신 방식

### 5.1 `POST /v1/ingest`
- 헤더: `Authorization: Bearer sp_pub_…` 또는 `sp_srv_…`, `Content-Type: application/json`.
- 본문 최대 64KB, 기록 최대 100건.
- 브라우저용 CORS 허용(`Origin` 무관, 키로만 판단).
- 처리 순서: 키 해시 조회(메모리 캐시 5분) → 크기·형식 검사 → 정제 → 묶음 안 합산 → Supabase RPC `ingest_batch` 1회 → 응답.
- 응답

| 코드 | 언제 | 앱이 할 일 |
|---|---|---|
| 202 | 받음 (`{"accepted": n, "dropped": m}`) | 없음 |
| 400 | 형식 오류 (`{"error": "…"}`) | 재전송 안 함 |
| 401 | 키 없음·틀림·폐기 | 재전송 안 함 |
| 413 | 64KB·100건 초과 | 나눠서 보냄 |
| 429 | 앱 한도 초과 (`Retry-After`) | 그 시간 동안 보내지 않음 |
| 503 | DB 장애 | 1번만 다시, 그래도 안 되면 버림 |

- 같은 `batch_id`는 한 번만 반영(중복 전송 방지, 24시간 기록).

### 5.2 `POST /v1/feature-map`
- 수집 키로 호출. 본문: `[{route, method, name}]` 최대 200개. **제안**으로만 저장, 회원이 S4·S10에서 확인해야 반영.

### 5.3 앱 쪽 전송 규칙 (연결 요청문으로 코딩 AI에 지시)
- 메모리에 모았다가 **30초마다 또는 50건이 차면** 한 번에 보냄. 브라우저는 페이지를 떠날 때 `navigator.sendBeacon`으로 남은 것 전송.
- 전송 실패가 앱 기능을 막으면 안 된다(비동기, 오류는 삼킴).
- 쉽앤핑 주소 자체로 가는 요청은 기록하지 않는다.

### 5.4 한도 (Workers 하루 10만 요청이 계정 전체라서) [제안]
- 앱당 하루 2,000 묶음, 1분 20 묶음. 메모리 카운터로 대략 세고 정확한 값은 DB에서.
- 무료 베타 최대 20개 앱. 계정 전체 하루 7만 요청을 넘으면 운영자 경보.

## 6. 요청문 틀

### 6.1 연결 요청문 (S4)
```
[쉽앤핑 연결 요청]
내 웹앱에 쉽앤핑 모니터링을 연결해 줘. 앱 기능은 바꾸지 말고 기록 전송만 추가해.

1. 서버(API 라우트, 서버 함수)가 있으면 모든 요청에 대해, 없으면 브라우저에서 데이터 저장·조회 요청에 대해
   주소 형태(route), method, status, 걸린 시간(ms), 오류 종류·메시지를 기록해.
2. 30초마다 또는 50건마다 묶어서 POST {INGEST_URL}/v1/ingest 로 보내.
   헤더 Authorization: Bearer {키}  (서버는 서버 키를 환경변수 SHIPPING_SERVER_KEY로, 브라우저는 수집 키)
   형식: {형식 예시 JSON}
3. app_version에는 배포마다 바뀌는 값(커밋 해시나 빌드 시각)을 넣어.
4. 절대 보내지 말 것: 입력값, 요청·응답 본문, 쿠키, 토큰, 쿼리 문자열, 주소 안의 실제 값(→ :id).
5. 전송 실패가 앱 동작을 막지 않게 해.
6. 앱 코드를 읽고 주소별 기능 이름(한국어, 사용자가 부르는 이름)을 만들어 POST {INGEST_URL}/v1/feature-map 으로 한 번 보내.
7. 끝나면 확인 방법: 앱을 한 번 써 보고, 응답 202가 왔는지 알려 줘.
서버 키는 코드에 직접 쓰지 말고 환경변수로. 깃에 올리지 마.
```
### 6.2 깊게 보기 추가 요청문 (S8)
기능 이름·시작·성공 기준 문장을 넣어 `attempt_start`·`attempt_result` 전송을 요청한다. "성공은 실제 저장이 끝난 곳(서버가 있으면 서버, 없으면 저장 응답을 받은 브라우저)에서 보내", "사용자가 취소하거나 화면을 떠나면 abandon" 포함.

### 6.3 AI에 보낼 내용 (S7)
```
[쉽앤핑 문제 보고]
기능: 분석 (POST /api/analyze)
상태: 최근 30분 24건 중 보통 3.4초 (평소 1.1초) — 2026-11-24 14:05부터
앱 버전: 3f2a9c1 (문제 시작 전 버전: 8b1e0d4)
실패한 단계: (깊게 보기일 때만)
오류 기록 (최근 5개, 개인정보 가림):
- 14:07 TimeoutError: upstream request exceeded 3000ms
- …
요청: 위 기능이 왜 느려졌는지(또는 실패하는지) 코드를 조사해 원인을 설명하고 고쳐 줘.
문제 시작 전 버전과 지금 버전 사이 바뀐 코드부터 봐 줘. 고친 뒤 배포하면 쉽앤핑이 실제 사용 결과로 확인한다.
```
- 복사 직전 4.3 정제를 한 번 더 적용한다. 키·이메일은 절대 넣지 않는다.

## 7. 판정 규칙 [PRD 5.4 구체화]

판정 Worker가 1분마다 RPC `evaluate_all()` 호출. DB 함수가 계산하고 바뀐 문제만 돌려준다.

| 규칙 | 계산 |
|---|---|
| 평소 속도 | 성공 30건 이상 & 첫 기록 후 3일 지남. 최근 7일 성공 요청의 중앙값·90% 지점. 6시간마다 다시 계산 |
| 실패 경보 | 최근 30분 결과(성공+실패) 5건 이상 & 실패 20% 이상, 또는 연속 실패 3건(깊게 보기) |
| 느려짐 경보 | 최근 30분 5건 이상 & 중앙값 ≥ 평소 중앙값 × 2. 평소 속도 없으면 느림 기준(기본 5초) 넘는 요청이 절반 이상 |
| 결과 미확인 | 깊게 보기 시도가 시작 후 10분간 결과 없음 → 미확인. 최근 1시간 미확인 50% 이상 & 10건 이상이면 "기록 전송이 끊겼을 수 있어요" |
| 묶기 | 같은 앱·기능·종류의 열린 문제가 있으면 새로 열지 않음 |
| 다시 알림 | 열린 문제의 지표가 처음 알림 때보다 2배 이상 나빠지고 마지막 알림 후 6시간 지남 |
| 해결 | 문제 시작 후 새 버전에서 결과 5건 연속 성공(느려짐은 평소 속도의 1.5배 이내) → 해결됐어요 + 알림 |
| 잠잠해짐 | 버전 변화 없이 2시간 동안 경보 기준 미만 → 잠잠해졌어요(알림 없음, 화면만) |
| 새 버전 | 앱에서 처음 보는 `app_version` → 버전 기록. 여러 버전이 섞여 와도(캐시·배포 중) 해결 판정은 문제 시작 후 처음 본 버전들의 기록만 |

## 9. 예외 처리

| 상황 | 처리 |
|---|---|
| 연결 후 30분 기록 없음 | S4 체크리스트 |
| 기록이 오다가 24시간 끊김 | 문제 아님. 앱 홈에 "하루 동안 기록이 없어요 — 사용자가 없었거나 연결이 끊겼을 수 있어요" |
| 사용량 0인 시간대 | 경보 판정 안 함(5건 미만) |
| 키 폐기 후 전송 | 401, 앱 홈에 "폐기한 키로 기록이 오고 있어요" |
| 앱 한도 초과 | 429, 앱 홈에 "기록이 너무 많아 일부만 받고 있어요" |
| Supabase 장애 | 수집 503, 판정 건너뜀, 운영자 Grafana 경보 |
| 슬랙 webhook 폐기·오류 | 이메일로 대체 + S9에 "슬랙 연결이 끊겼어요, 다시 연결해 주세요" |
| 메일 한도 | 묶음 메일로 |
| 시계가 어긋난 기록 | ±24시간 밖은 버림, `dropped`로 알려 줌 |
| 늦게 온 결과 | 미확인 → 성공/실패로 고침. 이미 보낸 알림은 그대로 |
| 버전 되돌리기(옛 버전 재배포) | 예전에 본 버전이어도 "다시 나타난 버전"으로 기록, 해결 판정에 사용 |
| 기능 이름표에 없는 주소 | "이름 없는 기능", 화면에서 이름 붙이기 |
| 주소 형태 200개 초과 | "기타"로 합침, S10에 안내 |
| 깊게 보기 결과를 브라우저 키로 `source=server` 전송 | 400 |
| 앱 삭제 | 키 즉시 무효, 모든 기록 삭제, 열린 문제 알림 중단 |
| 탈퇴 중 실패 | 이미 한 단계(키 폐기·앱 삭제)는 되돌리지 않고, [다시 시도] 때 남은 단계부터 이어서 한다. 로그인 계정 삭제 전에 실패하면 계정·로그인은 그대로 두고 S11에 "탈퇴를 마치지 못했어요" + [다시 시도]. 응답이 끊겨 결과를 모르면 세션 갱신으로 판별(계정 없음 → 완료, 있음 → 실패, S11 절) |

## 10. 완료 조건

| # | 조건 |
|---|---|
| C1 | 두 회원 A·B가 각자 앱을 등록했을 때 A는 B의 앱·기록·문제를 어떤 경로(화면, Supabase 직접 조회)로도 읽을 수 없다 — RLS 테스트 |
