# T24 서버 검증

베타 Worker는 요청 횟수를 isolate 메모리에 보관한다. 한 isolate에서는 회원별 30초에 탈퇴 요청을 두 번까지 허용한다. 새 isolate가 뜨면 횟수가 초기화되고 동시에 동작하는 isolate는 각자 요청을 센다. 키 조회 실패 한도와 앱별 수집 한도에도 같은 제약이 있다.

탈퇴는 인증으로 확인한 회원 ID로 먼저 DB에 2분간 유효한 진행 상태를 기록한다. 같은 회원의 유효한 상태가 있으면 다른 Worker도 429를 반환하고 앱·회원 삭제를 진행하지 않는다. 확정된 실패는 해당 요청의 토큰으로 해제하고, 응답 유실이나 Worker 중단 시에는 만료 후 다시 시도할 수 있다. Auth 회원이 삭제되면 외래 키가 진행 상태를 함께 지운다. pgTAP에서 중복 호출, 잘못된 토큰의 해제 시도, 만료, 재시도, 삭제 후 정리를 확인한다.

workerd HTTP 테스트는 메일 예약과 묶음 확장 RPC가 서로 다른 수신자 그룹에서 503을 반환하는 상황을 만든다. 두 그룹의 실패가 각각 현재 선점 토큰으로 완료 RPC에 전달되어 재시도로 집계되는지 확인한다. 다음 그룹의 메일 도착과 완료 처리를 검사하고 느려짐 알림에 평소 시간과 최근 시간이 차례로 들어가는지 확인한다.

## 3차 보안 검증

오류 메시지에서 순수 10자리 숫자는 모두 가린다. 초 단위 Unix 시각과 미국 전화번호가 같은 범위를 쓰기 때문이다. 구분자가 없는 13자리 숫자는 로그 시각을 읽을 수 있도록 1577836800000~2082758399999 범위의 밀리초만 보존한다. 이 범위에서도 앞 여섯 자리가 유효한 YYMMDD이고 일곱 번째 자리가 1~8이면 주민·외국인등록번호 모양이므로 가린다. Luhn을 통과하는 값도 가린다.

공통 시험표 190건에는 대소문자가 섞인 키 이름, 공백과 줄바꿈이 있는 JSON 객체, Authorization 헤더의 줄 끝까지의 값, 숫자 경계가 포함된다. 같은 10자리 숫자가 오류 메시지에서는 가려지고 앱 버전에서는 보존되며 경로에서는 `:id`가 되는지 검사한다.

## 4차 보안 검증

공통 시험표 끝의 이름 28개와 형태 40개를 조합해 1,120건을 만든다. Rust는 수집된 오류 예시를, 웹은 정제 함수와 표시 문자열을, pgTAP는 DB 정제 함수의 출력을 확인한다. 웹 테스트에서 pgTAP의 이름·템플릿도 원본 시험표와 대조한다. 고정 사례 193건에는 여러 쌍을 담은 Cookie, 속성이 붙은 Set-Cookie와 일반 단어 여섯 개가 포함된다.

민감한 이름 뒤에 콜론이 오는 헤더는 그 이름부터 줄 끝까지 가린다. 따라서 스킴 없는 값이나 Digest 매개변수, 쿠키 속성도 함께 사라진다. 따옴표로 감싼 JSON 키는 값의 범위를 계산해 다음 필드를 보존한다. 배열 안의 닫는 괄호가 이스케이프된 문자열에 들어 있는 경우도 검사한다.

### 남은 위험

사람 이름이나 집 주소처럼 민감한 필드명 없이 자유 텍스트에 쓰인 개인정보는 이 규칙으로 식별할 수 없다. 헤더와 같은 줄에 붙은 일반 진단 문구는 값과 경계가 모호해 함께 가려질 수 있다.

## 5차 정제 검증

등호형 Cookie와 Set-Cookie는 세미콜론 뒤의 쌍까지 줄 끝에서 함께 가린다. 계정·세션 식별자와 개인정보 필드도 기존 JSON, 이스케이프, 로그 대입 형태에서 값을 가린다. 이름과 주소에 공백이 들어갈 수 있어 따옴표 없는 개인정보 대입은 줄 끝까지 가린다. 오류 URL은 쿼리를 `?[가림]`으로, 경로의 숫자·UUID·16자 이상 영숫자 조각을 `:id`로 표시한다. 수집 경로에서도 긴 소문자 영문 조각이 `:id`가 되므로 같은 형태의 기존 라벨은 다시 확인해야 한다.

공통 시험표 201건과 이름 51개 × 형태 40개의 조합 2,040건을 Rust 수집·웹 표시·DB에서 대조했다. 설정 화면의 기능 이름도 이 정제를 거친다. `name=Jane Doe`나 `계정 user_id=sample`이 저장돼 있으면 입력 칸을 비우고 새 이름을 요구한다. 화면 테스트에서 일반 이름 ‘신청’으로 저장되는 것까지 확인했다. 웹 테스트 2,422건과 프로덕션 빌드, PostgreSQL 17의 정제 pgTAP 2,243건이 통과했다.

### 처리 시간과 역추적

정규화 전에 유니코드 코드 포인트 2,000개까지만 읽는다. 입력을 줄인 경우에는 최종 300자 중 다섯 자리를 `…[잘림]`에 배정한다. 자격 증명 값의 끝을 찾으면 그 안의 이름에 대해 같은 값을 다시 파싱하지 않는다. 세미콜론에서 바깥 값이 끝나더라도 그 안에서 시작한 쿠키는 별도 패턴으로 해당 줄 전체를 가린다.

로컬 Rust release에서 정규식 초기화 후 약 64KB 한 줄의 단일 필드를 측정했다. 대입 반복, Cookie 헤더 반복, 숫자 반복, 닫히지 않은 따옴표와 한글 입력에서 각 0.1ms 미만이었다. 테스트 상한은 release 10ms, 디버그 CI 100ms다. 이 측정 범위는 정제 함수 한 번이며 운영 Worker의 요청 전체 CPU 시간은 별도 측정 대상이다.

Rust의 regex 엔진은 백트래킹을 사용하지 않는다. 웹의 자격 증명·이메일 패턴에는 일치 실패 후 재시도할 수 있는 가변 길이 부분이 있다. 따옴표·배열의 닫힘 처리는 순방향 루프를 쓰고 세 구현 모두 정규식에 넘기는 원본 입력을 제한한다. 겹치는 구간은 정렬해서 합치므로 전체 파이프라인의 비용에는 구간 정렬도 포함된다.

### 남은 위험

필드명 없이 문장에 들어간 이름·주소는 식별할 수 없다. 긴 영문 경로, 쿠키와 같은 줄의 진단 문구, 실제 쿼리처럼 보이는 물음표 뒤 텍스트는 함께 가려질 수 있다.

## 7차 수정 — 오류 문구 최소 저장

사용자는 “1번하고 나중에 내가 qa 해보고 문제가 생기면 다시 요청할게”라고 결정했다. 자유 글 정제에 일곱 번의 검수 동안 새 빈틈이 발견되어, 오류 설명에서 남길 수 있는 값을 제한했다.

- `error_message`는 맨 앞 토큰이 `Error`, `Exception`, `Fault` 중 하나로 끝나는 영문 오류 종류 이름일 때만 그 이름을 저장한다. 점으로 구분한 패키지를 포함해 최대 60자다. 예를 들어 `TypeError: failed to save`는 `TypeError`가 되고 `nickname: Jane`은 NULL이 된다.
- `error_kind`는 `[A-Za-z0-9_.-]` 1~80자로 한정한다. 숫자가 4자리 이상 이어지거나 공백·콜론·등호·따옴표·슬래시·@가 있으면 NULL이다. `network`, `http_500`, `E404`는 저장한다.
- `step`은 40자 이내의 고정 식별자 또는 한글 단계 이름이며 한글 이름에 공백을 쓸 수 있다. 숫자 3자리 이상 연속, @, 등호, 콜론, 따옴표가 있으면 NULL이다.
- 키 접두사, Bearer, 이메일, 전화번호, 주민번호, Luhn 카드번호 패턴도 검사한다. Rust 수집, DB 저장, 화면·요청문 표시에서 같은 시험표를 사용한다. 저장할 수 없는 필드는 NULL로 두고 오류 종류가 비면 화면·요청문에 “(내용 저장 안 함)”을 표시한다.

기존 공통 시험표의 입력과 이름·형태 조합은 보존했다. 이전에 가린 이름이 다시 노출되는 것을 막기 위해 일반적인 `이름:`은 오류 클래스로 인정하지 않고, 오류 코드에서도 콜론을 제외했다. 날짜형 버전과 route는 별도의 기존 규칙을 적용한다.

64 KiB·100건 벤치는 세 진단 필드 300개를 정제한다. 이 작업 환경의 release 측정값은 36.042µs였다. route와 step에 앱이 직접 사용자 이름이나 주소를 넣으면 고정 이름과 구별하기 어렵다. 계측 코드는 고정 경로 템플릿과 고정 단계 이름을 보내야 한다.
