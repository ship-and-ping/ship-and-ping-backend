# T32 휴대폰 승인으로 PC 로그인

PC는 10분간 유효한 두 자리 숫자를 표시한다. 휴대폰에서 직접 입력한 숫자가 처음 틀리면 DB가 요청을 닫고 PC에 취소 사유를 전달한다. 승인 후 PC는 폴링 비밀값으로 암호화된 일회용 인증 값을 한 번만 수령해 독립 세션을 얻는다.

Worker는 요청별 256비트 승인 값을 Supabase 로그인·가입 메일 복귀 주소로만 보낸다. 요청 생성 응답에는 PC용 값만 담는다. 서버는 확인된 이메일, 요청별 승인 값, 요청 이후 최근 5분 이내의 OTP 인증 시각을 조회와 결정 양쪽에서 검증한다. 승인 요청을 만들 수 없으면 웹은 기존 Supabase 메일 로그인·가입을 계속한다.

## 검증

| 확인 항목 | 검증 방법 |
|---|---|
| 앞자리가 0인 숫자 직접 입력, 즉시 거절, 메일 링크 안내 | 웹 회귀 테스트. 변경 전 실패를 확인한 뒤 전체 2,821개 통과 |
| 승인 서비스 429·503 이후 일반 메일 로그인과 가입 | 두 경우 모두 Supabase 호출과 일반 로그인 복귀 주소를 검증 |
| 웹 정적 검사 | 로컬 ESLint와 프로덕션 빌드 통과 |
| PC 대기와 휴대폰 승인 화면 | Edge에서 390px·1440px 캡처 4장 갱신 |
| 요청별 메일 발송, PC 응답 필드 제한, 승인과 1회 수령 | PR의 Rust·workerd HTTP 통합 검사 |
| 오답 즉시 폐기·재시도 차단, 요청별 메일 값과 인증 시각, 권한과 제한 | PR의 Supabase pgTAP 검사 |

## 운영 적용

1. Supabase에 `supabase/migrations/20261126400000_login_requests.sql`을 적용한다. 운영 Pages 원점의 `/login/approve?req=*` 복귀 주소를 허용하고 로그인·가입 메일 양식을 적용한다.
2. Worker에 운영 Pages 원점 `WEB_ORIGIN`과 동일 프로젝트의 공개 키 `SUPABASE_PUBLISHABLE_KEY`를 설정하고 배포한다.
3. Pages를 배포한 뒤 운영 메일로 PC·휴대폰 왕복 로그인을 확인한다.
