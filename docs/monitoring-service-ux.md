# 쉽앤핑 사용자 흐름

## S1 기기 간 로그인 승인

| 상태 | 화면에서 보는 내용 | 다음 행동 |
|---|---|---|
| PC 메일 대기 | 확인 숫자, 휴대폰 승인 방법, 10분 기한 | 메일을 열거나 새 메일 요청 |
| 휴대폰 확인 | 요청 시각·브라우저·국가, PC 번호 보기 세 개 | 숫자를 고르고 승인하거나 바로 거절 |
| 숫자 불일치 | PC 숫자 다시 확인 안내 | 다시 선택, 세 번째 오답에 종료 |
| 승인 완료 | 휴대폰에 승인 완료 안내, PC는 로그인 후 화면으로 이동 | 각 기기에서 자기 세션 사용 |
| 거절·만료 | PC에 거절 또는 만료 사유 | 새 메일 요청 |
| 같은 브라우저 | 링크를 열면 요청 자동 완료 | 기존 로그인 후 화면으로 이동 |

## 고른 시안 (2026-11-25)

| 순서 | 사용자 말 (그대로) | 정해진 것 |
|---|---|---|
| 1 | "C가 좋아보이긴네" | D1 시안 C(한 문장 알림 카드)를 기본 방향으로 |
| 2 | "C로 하되 양 캐릭터는 B처럼" | 시안 B의 양 아바타와 말풍선을 가져온다 |
| 3 | 섞는 정도 "1: 가볍게 (추천)" | 맨 위 큰 퍼플 카드에만 양 아바타(36px)와 말풍선 꼬리를 붙여 양이 그 문장을 말하는 것처럼. 해결 때 양 둘레 민트 고리 한 번(동작 줄이기면 없음). Jua 글꼴·대화형 배치는 쓰지 않고 나머지 화면·목록은 C 그대로 |

- 고르지 않은 시안 A(조용한 상태 보드)·B(양이 먼저 말해 줘요)는 비교 기록으로 [`docs/design/mockups/`](design/mockups/compare.html)에 남긴다.
- 결과: [디자인 시스템](design-system.md), [S1~S10 최종 화면](design/final/index.html).
- 이 문서의 흐름·상태 문장은 시안 선택과 상관없이 그대로 쓴다. 최종 화면에 그린 상태: S4·S5·S7의 로딩·빈 화면·오류, S5 "모두 괜찮아요"와 큰 글자(200%), S7 "알림 링크로 처음 연 화면"과 "업데이트 후 확인 중".
- **D3 (2026-11-25, Codex 사후 검수 지적 반영)**: 사용자 선택(C + 양 가볍게)은 그대로 두고 빠진 화면과 상태를 채웠다. S4 ① 연결 요청 복사·②~④ 대기·복사 실패, S5 키보드로 기능 상세 열기·새 버전 감지 띠·큰 글자 메뉴, S6 7일 보기·보통 시간 선·실패율·오류 예시 5개, S7 첫 사용 대기·더 나빠짐·잠잠해졌어요·문제 아님으로 닫음, S8 첫 결과 대기·도착·결과 4가지, S9 미연결·연결 끊김, S10 숨긴 기능 되살리기·주소 200개 초과. 요청문은 기능명세서 6장 전문을 미리 보기로 보여 준다.
- **S11 내 계정 추가 (사용자 결정 2026-11-25, 그대로: "마이페이지도 추가해줘")**: 계정 정보, 앱마다 알림 받을 곳 요약, 앱 수, 로그아웃, 회원 탈퇴(확인·진행·실패·완료). 기능명세서 v1.1 S11.
- **D4 PC 우선 (2026-11-25)**: 사용자 지적 그대로 "근데 이거 웹페이지인데 앱만 너무 만든거 아니야?" → 사용자 결정 "A"(PC 우선으로 다시 그리고 소개 페이지 추가). 모든 화면을 PC 브라우저(왼쪽 메뉴 + 본문) 기준으로 다시 그리고, 로그인 전 첫 화면 S0 소개 페이지를 더했다. 방향(C + 양 가볍게)·토큰·문구는 그대로.

표시: **[가정]** 확인하지 않은 사용 환경·행동 추정 · **[명세]** 기능명세서에 이미 정해진 동작 · **[제안]** 이 문서의 제안(명세에 없음, 구현 전 확인 필요)

## 1. 대상·목표·사용 환경

| 항목 | 내용 |
|---|---|
| 대상 | 코딩 AI로 웹앱을 만들어 공개한 비전공 제작자(PRD 2장). 그래프·지표·로그를 읽지 않는다 |
| 목표 | 세 가지 답을 혼자 얻는다: **괜찮은지 / 어디가 문제인지 / 고쳐졌는지**. 성공 기준은 "연결부터 수정 결과 확인까지 혼자 끝낼 수 있는가"(PRD 6장) |
| 사용 환경 (D4에서 고침) | **PC 브라우저가 주 사용 환경, 알림을 받으면 휴대폰으로 확인.** 연결·복사·설정·기록 보기는 앱을 만들고 배포하는 자리(코딩 AI 대화창과 같은 PC 화면)에서 한다. 그래서 화면은 PC 브라우저(1440×900, 1280 확인)를 기준으로 그리고 휴대폰은 반응형으로 맞춘다([디자인 시스템 10장](design-system.md)) |
| 알림 받을 때 | **[가정]** 휴대폰 슬랙 알림을 먼저 보고 링크를 휴대폰 브라우저(슬랙 안 브라우저일 수 있음)로 열어 상황을 확인한다. 복사·붙여넣기·배포는 PC로 옮겨서 한다 |
| 처음 오는 사람 | 로그인 전 첫 화면은 S0 소개 페이지(D4 추가). 무엇을 해 주는지와 연결 3단계를 보고 [시작하기]로 S1 |
| 화면 밝기 | **[가정]** 밤에 알림을 받는 경우가 있어 어두운 모드를 기기 설정에 따라 자동으로 맞춘다 |
| 언어 | 쉬운 한국어. 백분위·p90·5xx·지연 시간 같은 말 대신 "보통 걸린 시간", "평소 속도", "실패" |

설계에 미치는 영향
- PC 화면은 왼쪽 메뉴(내 앱·알림 설정·내 계정) + 본문. 복사할 요청문은 넓게 펼쳐 읽고, 옆에 단계 안내를 둔다.
- 휴대폰 첫 화면(알림 링크로 연 S7)에서 **문장 한 줄과 숫자**만으로 상황이 이해돼야 한다. 그래프는 보조.
- 휴대폰에서 [AI에 보낼 내용 복사]를 눌러도 붙여넣을 곳은 PC일 수 있다. **[제안]** 복사 버튼 아래에 "PC에서 이어서 하려면 이 화면 주소를 열어 두세요" 한 줄 또는 [PC로 보내기: 이 링크를 내 메일로] 같은 보조 경로를 검토(첫 버전 필수 아님).

## 2. 핵심 흐름 — 문제 발견에서 해결 확인까지

```
[슬랙/이메일 알림]  "분석이 느려졌어요. 평소 1.1초 → 최근 30분 3.4초 (24건)"  [쉽앤핑에서 보기]
        │ (휴대폰에서 링크 열기 — 로그인 유지 중이면 바로, 아니면 로그인 후 같은 화면으로 돌아옴)
        ▼
S7 문제 상세  ── 쉬운 설명: 제목 문장 + 평소/최근 숫자 + 시작 시각 + 지금까지(감지→알림)
        │ [AI에 보낼 내용 복사]  → 버튼이 "복사했어요"로 바뀜, 화면 읽기에도 알림
        ▼
코딩 AI 대화창(쉽앤핑 밖)  ── 붙여넣기 → AI가 조사·수정 → 제작자가 배포
        │ (쉽앤핑은 기다림: "고친 버전을 배포하면 여기서 확인해 드려요")
        ▼
새 버전 감지  ── S7 업데이트 후 확인 영역이 단계별로 바뀜
        │  "업데이트 후 첫 사용을 기다리고 있어요" → "업데이트 후 3건 성공, 2건 더 확인할게요"
        ▼
해결 판정  ── "해결됐어요" + "업데이트 후 분석 15건 모두 평소 속도로 끝났어요" + 슬랙 알림 한 번
        └─ 새 버전에서도 실패 → "업데이트 후에도 5건 중 2건 실패했어요" + [AI에 다시 보낼 내용 복사](이전 시도 버전 포함)
```

| 단계 | 사용자가 하는 일 | 화면이 답하는 질문 | 누르는 횟수 |
|---|---|---|---|
| 알림 | 슬랙 메시지 읽기 → 링크 | 무엇이 문제인가 | 1 |
| 설명 | S7 읽기 | 얼마나 나쁜가, 언제부터인가 | 0 |
| 복사 | [AI에 보낼 내용 복사] | 무엇을 AI에 보내나 | 1 |
| 수정 | 쉽앤핑 밖 | — | — |
| 확인 | 기다림(또는 S7 다시 열기) | 고쳐졌나 | 0~1 |

- 문제 → 해결까지 쉽앤핑 안에서 누르는 곳은 **2번**(링크, 복사). 확인은 자동이고 해결 알림이 다시 온다.
- 뒤로 가기: S7의 헤더 뒤로 단추는 앱 홈(S5)으로. 브라우저 뒤로 가기도 같은 결과(주소에 문제 번호가 들어가 링크 공유·새로고침이 된다).

S1 로그인 ─ 이메일·비밀번호 또는 메일 링크 (Google 예정)

| 지점 | 왜 막히나 | 대응 |
|---|---|---|

| 평소 속도가 아직 없음 | 30건·3일 전 | "지금까지 7건, 0.9~2.1초"와 "평소 속도를 익히는 중"을 같이 보여 줌 |

## 4. 화면별 상태와 복구 경로 (S1~S11)

공통 규칙
- **로딩**: 화면 뼈대(제목·카드 자리)를 먼저 그리고 내용 자리는 옅은 막대로 채운다. 0.3초 안에 끝나는 조회는 로딩 표시를 하지 않는다. 버튼을 누른 뒤 서버 응답을 기다리는 동안 그 버튼은 "…하는 중" 글자와 함께 비활성화(중복 제출 방지).
- **오류**: 무엇이 안 됐는지 + 어떻게 하면 되는지를 한 문장씩. 오류 코드는 [자세히] 안에만. 오류 문구는 화면 읽기 프로그램에 바로 알린다.
- **완료**: 버튼 이름과 같은 말로 확인("복사" → "복사했어요", "등록" → "등록했어요").
- **상태 표시**: 괜찮아요(민트) / 문제 있어요(경고색) / 기록을 기다려요(회색) — 색 + 모양이 다른 아이콘 + 글자를 늘 같이.

## 6. 움직임 원칙 (emil-design-eng 기준)

값과 동작 줄이기 처리의 기준은 **[디자인 시스템 5장](design-system.md) 하나**다. 이 절은 흐름에서 지킬 원칙만 적고, 값이 다르면 디자인 시스템을 따른다(D3에서 두 문서를 맞춤).

- 상태가 바뀌어 보여 주는 움직임은 **드물게 일어나는 두 순간**뿐: 첫 기록 도착(S4), 해결됐어요(S7). 매일 보는 목록·표·숫자는 움직이지 않는다(숫자 세어 올리기 금지, 기간 바꾸기도 바로 바뀜).
- 그 밖에 쓰는 움직임은 누른 데 대한 반응(단추 0.97 눌림 0.16초, 스위치 손잡이)과 로딩 표시(스켈레톤 밝기, "…하는 중" 회전)뿐. 반복되는 움직임은 로딩 표시와 S0 소개 페이지의 큰 양에만 쓴다. 앱 화면의 양은 첫 기록 도착(뿔 핑)·해결(폴짝 + 민트 고리) 때 한 번.
- 0.16~0.7초, 강한 ease-out(`cubic-bezier(.23,1,.32,1)`), `transform`·`opacity`만.
- 기기의 **동작 줄이기**가 켜져 있으면: 상태 바뀜·해결 막대는 0.15초 투명도 변화만, 민트 고리·단추 눌림·스위치 미끄러짐 없음, 스켈레톤 멈춤. "…하는 중" 회전만 진행 중임을 알리는 필수 표시라 1.6초 주기로 느리게 남긴다.

| 완료 | 충족 | 단추와 같은 말로 확인, 해결 시 문장 자체가 바뀜 |
| 접근성 | 충족(시안 기준) / 일부 미확인 | 상태는 색 + 아이콘 모양 + 글자. 누르는 곳 44×44px 이상, 키보드 초점 3px 테두리, 아이콘만 있는 단추에 이름, 복사 결과를 화면 읽기에 알림, 동작 줄이기 대응. 명도 대비는 색 값으로 계산해 모두 AA 이상. **실제 브라우저·화면 읽기 프로그램으로는 확인하지 못함** |

## 8. 남은 가정과 확인할 것

| # | 가정 | 확인 방법 |

| 1 | 평소엔 PC, 알림은 휴대폰 슬랙 링크로 먼저 연다 | 베타 사용자 3~5명에게 알림을 어디서 보는지 묻기 |
