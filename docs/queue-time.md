# 요청 대기와 짧은 응답 멈춤

Trova 4차 시험에서 200명이 접속한 첫 3분의 클라이언트 p50은 560ms, p95는 1,934ms였다. 서버 안에서 측정한 places 평균은 127ms, bookmarks 평균은 91ms였다. 15:45:37~47에는 클라이언트 타임아웃이 124건이었고 수집된 실패는 0건이었다. CPU는 84~96%, steal은 62~73%였다. 서로 다른 통계량의 차이로 실제 대기 시간을 역산할 수 없다. 회귀 시험의 433ms 대기는 560ms 중 127ms를 처리에 썼다고 가정한 합성 표본이다.

## 어느 구간을 재는가

요청마다 수신 시각, 핸들러 진입, 응답 완료 또는 끊김을 관측한다. `duration_ms`는 수신부터 종료까지다. `queue_ms`는 그 안에서 핸들러를 기다린 구간이다. 경과 시간은 단조 시계로 잰다. 프록시의 실제 수신 시각을 쓰는 경우 핸들러 진입 때만 벽시계 차를 계산한 뒤 처리 시간을 더한다. 외부가 지정한 헤더를 신뢰하지 않는다.

| 환경 | 수신 시각 우선순위와 종료 관측 |
|---|---|
| nginx·호스팅 프록시 | 외부 헤더를 덮어쓰는 신뢰된 프록시에서만 X-Request-Start를 읽는다. nginx의 `t=${msec}`는 소수 초, Heroku 라우터는 Unix 밀리초다. 제공 여부와 단위를 배포 설정에서 확인한다. |
| Node | 프록시 다음으로 각 요청의 첫 request 이벤트에서 저장한 단조 시각을 사용한다. 응답 finish, 완료 전 close, 기한 타이머가 한 번만 결과를 남긴다. 소켓 생성 시각은 keep-alive 요청에서 재사용되므로 쓰지 않는다. |
| Tomcat·Spring | 프록시가 없으면 해당 버전의 Valve가 접근 가능한 Coyote 요청의 getStartTime()을 사용한다. 비동기 완료·오류·시간 초과와 연결 쓰기 실패를 함께 처리한다. |
| Python ASGI·Go | 신뢰된 프록시 또는 서버 어댑터의 요청별 수신 시각이 필요하다. 마지막 본문 쓰기와 취소·연결 오류를 관측한다. |
| 브라우저·수신 시각 미제공 서버 | 관측 가능한 요청 시간만 전송한다. queue_ms는 비운다. 브라우저는 응답 본문을 다 읽거나 요청이 취소된 시점까지 잰다. |

프록시 시각이 미래이거나 차이가 600,000ms를 넘으면 다음 출처를 사용한다. Worker는 0부터 duration_ms까지의 정수 대기 값만 합산한다. 누락·음수·범위 밖 값은 요청을 살리고 대기 집계에서만 제외한다. 평균 대기와 비중의 분모는 같은 대기 표본의 건수와 전체 시간 합이다. 비중이 50% 이상이면 AI가 T55의 서버 자원 부족 유형을 우선 조사하도록 CPU·스레드 풀·인스턴스 크기를 지목한다. 사건 구간에 T54가 측정한 CPU·steal 최댓값이 있으면 요청문에도 넣는다.

새 계측기는 응답 기한 timeout_ms를 명시한다(설정을 모르면 10,000ms). 기한을 넘은 200도 timeout이며 기한과 정확히 같은 완료는 성공할 수 있다. 클라이언트가 먼저 연결을 끊으면 aborted다. 이후 도착하는 완료 이벤트는 무시한다. 서비스가 멈춰 타이머나 전송 자체가 실행되지 못하면 프로세스가 회복되거나 외부 관측이 도착하기 전까지 알 수 없다. 기존 발신자의 필드와 판정은 유지한다. 요청·응답 본문, 원본 헤더·주소, 쿠키·계정 값은 수집하지 않는다.

## 10초 멈춤 판정

매분 최근 약 100초를 되짚어, 끊김·기한 초과가 포함된 연속 10초 구간을 1초씩 옮겨 검사한다. 기능별로 다음 조건을 모두 충족해야 한다.

1. 구간 직전 3분 각각에 정상적으로 끝까지 응답한 요청이 30건 이상이며 직전 5초에 완료 응답이 있다. 분당 30건이면 통상 10초에 약 5개 응답을 기대할 수 있다. 세 분과 최근 완료를 모두 요구해 단발성 트래픽과 영업 종료를 걸러 낸다.
2. 해당 10초에 완료 응답이 0건이고 aborted 또는 timeout이 3건 이상이다. 일반 HTTP 오류 응답도 끝까지 보내면 흐름이 이어진 것으로 센다. 기한을 넘긴 완료는 timeout으로 센다.
3. 기존 기능별 failure 문제로 열어 같은 문제의 알림·해결·숨김 규칙을 적용한다. T54의 silent는 앱 전체에서 10분 동안 서버 기록이 도착하지 않은 경우다.

초별 완료·중단 건수는 비공개 테이블에 6분간 보관하고 매분 만료시킨다. 시간은 묶음을 받은 시각 대신 결과 관측 시각을 쓴다. 30초 배치 전송과 매분 판정에 따라 실제 알림은 늦을 수 있다.

측정 API의 단위와 종료 이벤트는 [Heroku 라우팅](https://devcenter.heroku.com/articles/http-routing), [Tomcat Coyote Request](https://tomcat.apache.org/tomcat-10.1-doc/api/org/apache/coyote/Request.html), [Node HTTP](https://nodejs.org/api/http.html)를 참고한다.
